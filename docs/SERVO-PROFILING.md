# Профилирование Servo на handheld

## Включение

Создать пустой файл `zimlite/servo/profile.enabled` рядом с установленным
приложением либо установить `ZIMLITE_PROFILE=1` для PortMaster launcher.
Запустить Zimlite обычным способом и открыть проблемную статью.
Профилирование не запускает статью автоматически и не меняет выбор движка.

Во время работы файлы находятся в `/tmp/zimlite-profile.XXXXXX/` (путь
выводится launcher). После обычного выхода они копируются в
`zimlite/profiles/UTC-ДАТА-PID/`:

| Файл | Содержимое |
| --- | --- |
| `app.log` | Обычный журнал приложения и stderr helper; этапы инициализации EGL, ServoBuilder, WebView, screenshot с памятью helper |
| `events.jsonl` | Начало/конец открытия статьи, preflight, чтение ресурсов с размером/MIME/временем, PID helper, первый кадр, watchdog, ошибки и закрытие; каждую секунду статистика Go heap/GC/стека/goroutines/cgo |
| `system.log` | Каждую секунду RAM/swap/Slab/CMA/Dirty системы, CPU ticks, page faults/активность reclaim, PSI при наличии, RSS/HWM/Swap/Threads и ожидание процессов Zimlite/Servo |
| `system.previous.log` | Предыдущая часть системного журнала после ротации |
| `kernel.log` | Снимок dmesg каждые 5 секунд, включая сообщения OOM и драйверов |

Каждые 5 секунд системный сборщик дополнительно читает PSS/private memory
из `smaps_rollup`, если ядро предоставляет его, и `wchan` потоков.
Он работает отдельным процессом: блокировка потока SDL не останавливает
сбор данных. При зависании всего ядра новые записи невозможны.
Синхронные `fsync`/`sync` во время рендеринга отключены: на исследуемом
KNULLI `/userdata` использует FUSE, а запуск с подробными журналами на этом
разделе зависал до Servo. Та же диагностика с журналами в tmpfs завершилась.
Логи в `/tmp` пропадут при перезагрузке. Для расследования полного зависания
нужно читать/сохранять их по SSH на компьютере до перезагрузки. Временные
логи занимают RAM и влияют на расход памяти.

`events.jsonl` ограничен 16 МиБ за запуск; после достижения лимита новые
события не записываются. `system.log` ротируется примерно на 16 МиБ,
сохраняются две последние части. `app.log` и число папок запусков не
ограничены: нужные журналы следует сохранить, остальные удалить вручную.
Тексты статей, токены HTTP и окружение процессов не записываются;
пути/названия статей присутствуют в событиях.

## Динамический резерв памяти

Текущая политика проверяет Linux `MemAvailable` каждые 100 мс. Когда остаётся
менее 50 МиБ (51200 КиБ), helper завершается, а текущая статья открывается
через SDL с восстановлением позиции. При таком остатке новый helper также
не запускается. Фиксированные пределы RSS helper и RSS+swap app + helper
заменены этой проверкой; лимиты ресурсов, IPC и времени первого кадра сохранены.
`MemAvailable` учитывает освобождаемые кеши, поэтому `MemFree` не используется.

В `events.jsonl`: `servo.watchdog` содержит порог и период проверки;
`servo.memory_available` раз в секунду — доступную память;
`servo.memory_pressure` — значение в момент переключения. В обычном журнале
при переключении появляется предупреждение с остатком и порогом.
Если ядро не предоставляет `MemAvailable`, событие
`servo.memory_monitor_unavailable` сообщает, что проверка памяти недоступна.
Проверка не гарантирует защиту от резкого выделения памяти между отсчётами.
Автоматического возвращения на Servo в текущей статье нет.

## После зависания

До перезагрузки сохранить текущую папку `/tmp/zimlite-profile.XXXXXX/` через
SSH. После нормального выхода архив находится в `profiles/` и следующий
запуск создаст другую папку. `kernel.log` в архиве относится к запуску;
новый `dmesg` после перезагрузки обычно уже не содержит сбоя.

Для отключения удалить `servo/profile.enabled` и убрать переменные
`ZIMLITE_PROFILE`/`KIWIX_PROFILE_DIR`, если они были заданы вручную.

## Как читать

- Рост Go `heap_alloc` сопоставлять с RSS приложения; остаток может включать
  libzim, SDL и другие native allocations, а также отображённые файлы.
- Рост RSS/Swap helper сопоставлять с этапами Servo и размерами ресурсов.
- Низкий MemAvailable, рост SUnreclaim/CMA/reclaim и сообщения ядра помогают
  отличить давление RAM от блокировки драйвера. Суммирование RSS процессов
  повторно учитывает общие страницы; PSS точнее, когда доступен.
- `resource.begin` без `resource.end` отмечает незавершённое чтение или
  ожидание блокировки libzim. `servo.close.begin` без `servo.close.end`
  отмечает ожидание завершения helper/HTTP/source.
- RSS/PSS не охватывает все выделения GPU. Отсутствие OOM в логе само по себе
  не исключает нехватку памяти или зависание драйвера.
