# План добавления Servo в zimlite

Дата исследования: 2026-10-10. Статус: план до реализации.

## 1. Задача и исходные допущения

Добавить Servo как второй движок отображения статей. Существующий SDL-движок
остаётся доступным и выбранным по умолчанию. Пользователь выбирает движок в
настройках и может переоткрыть текущую статью другим движком.

Требование пользователя: Servo должен работать на всех Linux handheld,
поддерживаемых PortMaster, с 1 ГБ ОЗУ. Память — на всю систему, включая ОС
и графический драйвер. TrimUI Smart Pro является только одной проверочной
платформой: текущий `Dockerfile.arm64` рассчитан на glibc 2.33 / libstdc++
6.0.28 и не доказывает совместимость со всем набором устройств.
Windows и desktop используются как вспомогательные платформы разработки.

До выбора минимального sysroot составить матрицу всех пар устройство/прошивка
из данных PortMaster с 1 ГБ RAM: CPU, userspace architecture, libc/ABI,
GPU/driver, SDL video backend, разрешение, доступная память, контроллеры.
Не приравнивать 64-битный CPU к 64-битному userspace.
Источники: [данные устройств PortMaster](https://github.com/PortsMaster/PortMaster-Info/blob/main/device_info.json),
[поддерживаемые устройства](https://portmaster.games/supported-devices.html),
[определение архитектуры](https://github.com/PortsMaster/PortMaster-GUI/blob/main/PortMaster/device_info.txt).

Servo описывает поддерживаемую Linux-платформу как 64-битную.
Если в целевой матрице есть только 32-битный userspace, необходим отдельный
эксперимент с портированием Servo и его зависимостей под armhf. Это возможный
блокер требования «все устройства», а не разрешение исключить такие устройства.
Источник: [Servo README](https://github.com/servo/servo#readme).

План основан на рабочем дереве после stash изменений клавиатуры. Ранее
сохранённые изменения не являются зависимостью этой работы. Этот документ
не подтверждает успешную сборку или приемлемое потребление памяти Servo.

## 2. Что установлено при исследовании

### zimlite

- `internal/storage/storage.go`: HTML-файл и главная страница ZIM сразу
  преобразуются в `document.Document` через `html.Parse`.
- `internal/html/parser.go`: цепочка HTML → Markdown → Document теряет CSS
  и исходную структуру страницы. Этот результат недостаточен для Servo.
- `internal/ui/loader.go`: владеет ZIM reader, навигацией и `docCache`;
  кеш документов — map без ограничения размера. `loadResource` рассчитан
  прежде всего на изображения, а Servo нужны также CSS, шрифты и другие данные
  с корректными URL, MIME и статусами ошибок.
- `internal/ui/interfaces.go`: текущие `DocViewer`, `LinkBrowser`, `Scroller`
  сочетают операции над документом и деревом. Их нельзя механически реализовать
  поверх WebView без определения семантики фокуса, якорей и истории.
- `internal/renderer/renderer.go` / `draw.go`: Renderer владеет окном SDL,
  кешами, рисованием статьи, строкой состояния и `Present()`.
- `internal/ui/ui.go`: приложение владеет историей и циклом SDL;
  настройки пока содержат язык, тему и размер шрифта.

### Образец подключения библиотек из glitchscope

В `glitchscope/.gitmodules` исходники библиотек подключены как Git submodule
под `lib/`. `Dockerfile.builder` собирает зависимости для amd64 и arm64
в `/opt/<library>/<arch>`. Изменения upstream оформляются файлами в `patches/`
и применяются при сборке. Makefile использует builder, упаковка переносит
нужные runtime-библиотеки и лицензии; см. также
`scripts/collect-portmaster-licenses.sh` и `Dockerfile`.

Для Servo используем ту же модель хранения исходников и воспроизводимой сборки.
Servo написан на Rust, поэтому форма линковки будет соответствовать его Rust API.

### Servo: подтверждённые возможности и ограничения

Rust API предоставляет Servo, WebView, RenderingContext, пробуждение event loop
и передачу событий ввода. Официальный пример показывает цикл создания,
`spin_event_loop`, `paint` и обработки scroll/resize.
Источники: [описание API](https://github.com/servo/servo/blob/main/components/servo/lib.rs),
[минимальный embedder](https://github.com/servo/servo/blob/main/components/servo/examples/winit_minimal.rs).

Есть `SoftwareRenderingContext`: программная реализация OpenGL и получение
RGBA через `read_to_image`. Документация предупреждает о низкой производительности.
Это полезная отправная точка для прототипа, а не доказательство пригодности
для портативного устройства.
Источник: [SoftwareRenderingContext](https://doc.servo.org/servo/struct.SoftwareRenderingContext.html).

Upstream также содержит C API, собираемый как `cdylib`; его описание обозначает
стабильный ABI как будущую цель. В изученном файле создания rendering context
экспортируется программный вариант. Поэтому C API не принимаем за готовый
универсальный SDL/GLES адаптер.
Источники: [C API README](https://github.com/servo/servo/blob/main/ffi/capi/README.md),
[manifest](https://github.com/servo/servo/blob/main/ffi/capi/Cargo.toml),
[rendering context](https://github.com/servo/servo/blob/main/ffi/capi/rendering_context.rs).

У Rust crate есть переключатели JIT, multiprocess, multimedia и web features.
Отключение JIT не удаляет JavaScript-движок. Минимальный набор зависимостей
нужно проверять сборкой выбранной версии.
Источник: [Servo Cargo.toml](https://github.com/servo/servo/blob/main/components/servo/Cargo.toml).

API имеет intercept загрузки HTTP-ресурсов и управление запросами навигации;
их пригодность для выбранной версии проверяем в прототипе.
Источник: [WebViewDelegate](https://github.com/servo/servo/blob/main/components/servo/webview_delegate.rs).

Ссылки на `main` описывают изученный upstream и могут измениться. На первом этапе
зафиксировать SHA submodule, toolchain, Cargo.lock и ссылки на тот же commit.
Публичного гарантированного бюджета Servo для устройства с 1 ГБ в изученных
источниках нет; приведённые ниже цифры являются проектными целями.

## 3. Предлагаемая архитектура

```text
App / Settings / Navigation
          |
   ArticleController ---- ContentSource (HTML, MIME, URL, ZIM resources)
          |
          +-- NativeArticleBackend --> текущий renderer
          |
          +-- ServoArticleBackend --> ограниченный IPC --> zimlite-servo-host
                                                         Rust + libservo
                                      RGBA viewport <---- RenderingContext
          |
   SDL compositor --> статья + строка состояния --> Present один раз
```

### Исходники и сборка

1. Добавить `lib/servo` как submodule `https://github.com/servo/servo` с
   закреплённым SHA. Не копировать дерево исходников в Go package.
2. Создать собственный Rust embedder `native/servo-host/` с зависимостью
   на crate `servo` из submodule. Собирать `zimlite-servo-host`, использующий
   движок как библиотеку; servoshell не используется как внешний браузер.
3. Собрать библиотеку и helper в Docker builder. Добавить Rust toolchain
   выбранного Servo, отдельные host/target зависимости, sysroot, cross linker
   и кеш Cargo для `aarch64-unknown-linux-gnu` и desktop amd64. Минимальный
   ABI выбирать по матрице PortMaster, а не только по TrimUI. При необходимости
   добавить несколько runtime-вариантов и выбирать их в launcher. Проверку
   armhf выполнять до обещания полного охвата.
4. Начать с `default-features = false`; включать только необходимые resources
   и fonts после проверки manifest. Не включать WebGPU, WebXR, WebGL,
   GStreamer и внутренний multiprocess Servo без потребности. Проверить
   сборку без `js_jit`; выбирать её по измерениям, а не только размеру бинарника.
5. Патчи при необходимости хранить в `patches/servo-*.patch`, применять
   к build-копии с проверкой соответствия закреплённому SHA. Не оставлять
   незадокументированные изменения в submodule.
6. Добавить Makefile targets для submodules, Servo builder и сборок с Servo;
   сохранить сборку базового варианта без Rust. Упаковывать helper, runtime
   зависимости, ресурсы/шрифты, notices Servo и транзитивных crates.
   Проверять runtime ABI на целевой прошивке. GPU-библиотеки брать из прошивки,
   не подменять их desktop Mesa из builder.

### Почему отдельный helper

Основной Go-процесс сохраняет SDL, навигацию и чтение ZIM. Helper владеет одним
Servo и одним активным WebView. Он запускается только при открытии статьи
через Servo. При выборе обычного движка завершается, что освобождает память
движка и его allocator. Это также позволяет показать ошибку и восстановить
статью после падения helper. Сам по себе helper не является sandbox и не
гарантирует защиту от системного OOM.

Go адаптер разместить в `internal/servo/`, без деталей DOM и Rust в App.
Для IPC задать версию протокола, handshake, лимиты размеров сообщений,
таймауты, request ID и generation статьи. События старого документа отбрасывать.
Команды: открыть, resize, scroll, pointer/touch, выбрать/открыть ссылку,
zoom/theme, snapshot/restore состояния, stop. Ответы: загрузка, кадр, URL,
фокус/scroll, ресурсный запрос, ошибка.

Rust объекты использовать на потоке helper, который создал Servo; wake callback
будит его loop. Go читает ответы в worker и уведомляет SDL через UserEvent.
SDL texture обновляется только на главном SDL-потоке. IPC и ZIM чтение
не должны блокировать этот поток; доступ к libzim сериализовать либо проверить
и обеспечить допустимую модель конкурентного чтения.

### Контент и ресурсы

Выделить `ArticleSource`: идентификатор архива/файла, канонический URL, MIME,
ленивое чтение оригинального HTML и ресурсов. Native backend по необходимости
строит существующий `document.Document`; Servo получает оригинальный HTML.
Не хранить одновременно HTML, Markdown, Document и DOM для каждой статьи.

Базовый путь прототипа — локальный origin вида
`http://zimlite.invalid/<archive-id>/<article-path>` с перехватом HTTP-запросов
в Rust delegate и выдачей данных через IPC из ContentSource. Это синтетический
origin: реальные DNS/HTTP-запросы к нему запрещены. Проверить перехват главного
документа и всех subresources до принятия решения. Если выбранный API не
позволяет реализовать его полностью, использовать loopback HTTP server на
случайном порту с токеном сессии; этот выбор фиксируется результатами этапа 1.

Сохранять относительные пути CSS, `url(...)`, query, fragments и redirects.
Резолвить их от URL запрошенного документа/stylesheet, а не изменяемого
глобального «текущего документа». Для файлов ограничить ресурсы каталогом
открытого файла. Отсутствующие ресурсы возвращают ошибки с корректным статусом.
Не распаковывать архив целиком и не строить кеш всех ресурсов заранее.

Навигация по ссылкам возвращается App: только App меняет историю и текущую
статью. Якоря внутри страницы обрабатывает выбранный backend. Внешние ссылки
сохраняют текущую политику открытия. Загрузка внешних ресурсов статьи
по умолчанию отключена для офлайн-режима; загрузчик библиотеки zimlite работает
по своей существующей схеме.

### Отображение и ввод

Первый прототип: software context → RGBA только видимого viewport → SDL
streaming texture. Выделить `BeginFrame`, `DrawArticle`, `DrawChrome`, `EndFrame`
из текущего Render, сохранив возможность обычного Render. Present остаётся
единственным для обоих backend. Не создавать картинку высотой во всю статью.

Обновлять текстуру только при новом кадре, объединять resize/scroll events,
ограничить очередь до последнего готового кадра. Для прототипа допустим
bounded binary transport; при заметных затратах копирования перейти к двум
shared-memory slots с подтверждением освобождения. Проверить pixel format,
stride, альфа-канал, ориентацию и viewport без строки состояния.

Software путь проверить на каждой группе CPU/userspace, поскольку отсутствие
аппаратного EGL не должно само по себе исключать устройство. Если software
rendering не обеспечивает приемлемую прокрутку, следующий
эксперимент — OffscreenRenderingContext с EGL/GLES и чтением viewport.
Поддержку драйвера и стоимость readback измерить отдельно. Передачу GPU textures
между процессами не включать в первую реализацию. Если оба пути не подходят,
Servo на этом устройстве остаётся недоступным до решения проблемы; требование
полного охвата в таком состоянии не считается выполненным.

Добавить backend interface в отдельном пакете `internal/article/`, без SDL
типов и зависимости от `internal/ui`. Native adapter использует существующий
renderer; дерево, настройки, помощь и меню продолжают работать через него.
App хранит активный backend и направляет ему действия статьи.

Нужны прежние действия gamepad: scroll/page, next/previous link, open, back,
home, tree, zoom. Сначала проверить нативное перемещение фокуса WebView
через Tab/Shift-Tab/Enter. Для соответствия существующей навигации по ссылкам
проверить DOM adapter: выделение только ссылок, URL и стабильный ID фокуса.
Возможность служебного DOM доступа при отключённых скриптах статьи — отдельная
проверка этапа 1; не обещать её без прототипа.

Состояние истории хранить отдельно для каждого движка: scroll, anchor,
фокус ссылки и zoom. Координаты native и Servo не эквивалентны. При переключении
впервые восстанавливать ближайший известный anchor или начало; при повторном
возврате — собственное состояние движка. Переход между движками не создаёт
новую запись истории. Тема Servo задаётся аккуратным user stylesheet;
исходные стили статьи сохраняются, точное совпадение тем не гарантируется.

## 4. Бюджет памяти для устройства с 1 ГБ

Первоначальные цели, которые уточняются измерением MemTotal/MemAvailable на
устройстве без zimlite. Размеры ниже в MiB; нельзя считать 1 ГБ полностью
доступным приложению или полагаться на swap.

| Область | Начальная цель |
|---|---:|
| Основной zimlite: Go, libzim, каталог, UI, кеши | до 150 MiB |
| Servo helper: DOM/layout/JS/fonts/rendering, включая software framebuffer | до 400 MiB |
| Дополнительные IPC buffers и SDL viewport texture | до 16 MiB |
| Цель суммарного устойчивого потребления приложения | до 600 MiB |
| Верхняя приемочная граница пика приложения | до 700 MiB, только при наличии запаса ОС |

Это ограничения для приемки, а не ожидаемое фактическое потребление Servo.
Приоритет — оставить измеренный запас для ОС/драйвера; при большом расходе
прошивки допустимый лимит приложения снижается. GPU/shared память учитывать
отдельно: одна сумма RSS не описывает всю занятую память.

Два RGBA viewport 1280×720 занимают около 7 MiB; это только кадры, а не весь
WebRender, DOM, JS heap, декодированные картинки и кеши. Ограничение кадров
не ограничивает память страницы.

Обязательные меры:

- Один WebView, без вкладок и фоновых страниц. Освобождать старую страницу
  при навигации; не держать DOM всей истории. Helper останавливать при выборе
  native; при длительном выходе в меню/дерево — тоже, восстанавливая по URL.
- Заменить неограниченный docCache на LRU с бюджетом, первоначально 16 MiB.
  При eviction история должна перечитать исходник: нынешний Back зависит
  от наличия записи в docCache. Бюджет считать с учётом структур Document,
  а не только длины HTML. Кеш ресурсов — отдельный, первоначально 16 MiB.
- Ограничить объём HTML на статью, число и суммарные байты ресурсов,
  размеры декодированных изображений, concurrent loads и pending IPC.
  Предварительные пределы: HTML 8 MiB, ресурс 16 MiB, IPC frame по viewport.
  При превышении показывать причину и предлагать обычный движок.
- Лимит по compressed bytes недостаточен для изображений: проверять размеры
  до декодирования и проверить, где Servo позволяет поставить такой контроль.
  Большой DOM может превысить память даже при небольшом исходном HTML.
- На первом этапе отключить скрипты контента доступным preference/API,
  мультимедиа и лишние web features. JavaScript runtime всё равно может
  присутствовать. JS-архивы, которым скрипты нужны для содержания, оценить
  отдельно после подтверждения бюджета статических страниц.
- Снимать RSS/PSS, peak, MemAvailable и показатели драйвера, когда доступны.
  Go heap не учитывает Rust/C++/GPU. При падении доступной памяти остановить
  helper до загрузки следующей статьи и предложить native.
- Если доступны cgroups, ограничить helper и проверить восстановление после
  OOM внутри его группы. Без cgroups мониторинг является только best effort;
  RLIMIT_AS не выбирать по RSS, поскольку reserved address space может быть
  значительно больше физического потребления.
- Измерить существующий `ListArticles` и radix tree на большом ZIM:
  полный каталог сам может съесть бюджет основного процесса. Если цель 150 MiB
  не выдерживается, включить отдельный этап ленивого/постраничного индекса.

## 5. Выбор движка пользователем

В Config добавить `article_renderer: native | servo`, старые config получают
`native`. SettingsPage показывает «Обычный» и «Servo» и сохраняет выбор.
Изменить config, settings URL parsing, menu template и все локализации.

Отдельно показывать фактически активный движок и причину недоступности Servo
(отсутствующий helper, несовместимый runtime, недостаточная память). Не выдавать
native за успешное включение Servo. После ошибки разрешить явное открытие
обычным движком; избегать бесконечных автоматических перезапусков helper.

Выбор относится к HTML/статьям ZIM. Markdown и служебные экраны в первой версии
используют обычный движок. В сборке без Servo вариант виден как недоступный
с понятным пояснением. Переключение текущей статьи сохраняет её идентификатор
и историю; при ошибке старый backend и документ остаются рабочими.

## 6. Этапы реализации и условия перехода

### Этап 1 — проверка реализуемости до общего рефакторинга

Сначала составить матрицу устройств/прошивок с 1 ГБ, объединить только
эквивалентные ABI/CPU/driver комбинации и определить минимальный runtime ABI.
Зафиксировать Servo submodule/toolchain и собрать минимальный helper сначала
amd64, затем ARM64 с этим ABI; проверить armhf, если он требуется матрицей.
Получить software RGBA frame,
CSS/картинку/шрифт из локального источника, scroll/resize/link events.
Проверить отключение content JS, навигацию фокуса и перехват всех ресурсов.
Снять память и задержки на настоящих устройствах: начать с самых слабых CPU
и наиболее ограниченных прошивок, затем охватить каждую группу матрицы,
включая software-only и разные SDL video backends. Использовать обычную
и тяжёлую статью.
Зафиксировать результаты в `docs/SERVO-PROTOTYPE-RESULTS.md` с SHA, firmware,
backend, разрешением, настройками, ZIM и таблицей измерений.

Условие перехода: рабочий ABI, получение кадра, офлайн-ресурсы, управление
геймпадом, память в бюджете и пригодная скорость. Предварительная цель:
прокрутка хотя бы 20 fps на типичной статье и отклик ввода p95 до 100 ms;
это приемочная цель, не обещанная характеристика. Результат одного TrimUI
не является подтверждением остальных устройств. Если software не проходит,
проверить GPU offscreen. Если целевой аппарат не проходит, оформить конкретный
блокер до полной интеграции. Оставить требование всех handheld явным:
fallback на native обеспечивает работоспособность zimlite, но не заменяет
поддержку Servo на соответствующем устройстве.

### Этап 2 — общая модель статей и ограниченные кеши

Реализовать IPC lifecycle и resource bridge, SDL compositor, события и ввод,

### Этап 4 — настройки и упаковка

Добавить выбор и состояние доступности в UI, локализации и help. Обновить

### Этап 5 — приемка на устройстве

Проверить обычные и длинные статьи, таблицы, формулы/SVG, крупные и битые
изображения, Unicode, CSS/fonts, relative URL, redirects, fragments и

Выполнить 100 последовательных переходов и 50 переключений движков;
проверить память в устойчивом режиме, пики загрузки, завершение helper,
поведение при таймауте/краше/нехватке памяти. Сравнить native до/после на тех же
статьях. При наличии GPU пути измерить также память драйвера и readback.

Автоматические проверки при реализации: config/default/validation,
URL/resource resolution, история после eviction, backend switching и IPC
limits/stale responses. После изменений кода — `make test && make lint`
по AGENTS.md, Docker cross-build и установка итогового PortMaster package
на устройства из матрицы. Для каждой пары устройство/прошивка отмечать
«проверено», «эквивалентная группа» или «не проверено», с основанием для
эквивалентности; полный охват не заявлять при известных несовместимостях.
Актуальное состояние реализации приведено в разделе 8 и документе результатов.

## 7. Что уточнить перед аппаратной приемкой

Целевой набор уже задан: все Linux handheld PortMaster с 1 ГБ ОЗУ.
Перечень, прошивки и разрешения получить из PortMaster; не перекладывать
составление списка на пользователя. Для аппаратной приемки потребуется
доступ к представителям групп матрицы либо результаты проверок на них.
Особенно важны runtime ABI, software rendering, EGL/GLES и MemAvailable.

Первый вариант рассчитан на статические HTML-статьи со стилями и изображениями.
Если обязательны интерактивные ZIM-приложения со скриптами, включить их в набор
приемочных архивов и пересмотреть бюджет после прототипа.

## 8. Ход реализации

Реализация начата: закреплён Servo, получены desktop и ARM64 кадры;
добавлены источники HTML/ZIM, persistent IPC, SDL compositor, выбор движка,
навигация и fallback. На TrimUI Smart Pro/KNULLI первая небольшая статья
1280×696 получена за 3,089 s с VmHWM helper 79,7 MiB. Это не полный замер
приложения и не приемка всех устройств. Детальные результаты и оставшиеся
проверки: [SERVO-PROTOTYPE-RESULTS.md](SERVO-PROTOTYPE-RESULTS.md).

Общий пакет собирается отдельно через `make dist-portmaster-servo`.
Минимальный ABI проверяется по ELF helper и runtime зависимостей, с отказом
упаковки при GLIBC >2.30. ARM64 runtime собран и прошёл аудит; архив
`dist/zimlite-servo.zip` создан. Для устройств без рабочего GLES 3 включён
отдельный software Mesa runtime; он используется только helper, не меняет
драйверы прошивки и проходит тот же ABI аудит. Watchdog дополнительно
останавливает helper при сумме RSS+swap Go приложения и helper более 600 MiB;
GPU allocations и краткие превышения остаются вне его гарантии.
